# Наради → задачі

Ви вставляєте транскрипцію наради. Система знаходить у ній усе, що люди
пообіцяли, створює задачі в Notion і надсилає кожному його задачі в Telegram —
з кнопками «Готово», «Відкласти», «Не актуально». Через тиждень ви одним рядком
бачите, скільки з обіцяного справді зроблено.

**Вона не вміє нічого видаляти.** Створити задачу й змінити їй статус — так.
Видалити задачу, сторінку чи повідомлення — ні, такого коду в ній немає.

---

## Що ви отримуєте

| Крок | Результат |
|---|---|
| Розбір | Таблиця: хто, що, до якої дати, наскільки терміново — з дослівною цитатою з розмови |
| Notion | Задача в базі «Домовленості» зі статусом, напрямом і посиланням на нараду |
| Telegram | Кожному — його задачі окремими повідомленнями з трьома кнопками |
| Кнопка | Натискання одразу міняє статус у Notion, без вашої участі |
| Звіт | «Зроблено / прострочено / у роботі» і відсоток виконаного |

Цитата в задачі — не прикраса. Це те, чим людина може заперечити: «я такого
не казав». Якщо цитати немає, суперечка впирається у вашу памʼять проти її.

---

## Спершу подивіться, як воно працює

Нічого налаштовувати не треба — демо не торкається ні мережі, ні ваших даних:

```bash
cd meetings
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python tools/demo_run.py
```

Побачите весь шлях на вигаданій нараді: транскрипцію, знайдені домовленості,
повідомлення, які отримали б люди, натискання кнопок і підсумковий звіт.
У демо одну людину навмисно не внесено в реєстр — так видно, як система про
це попереджає замість того, щоб мовчки загубити задачу.

## Що потрібно від вас

### 1. Ключ до ШІ (5 хвилин)

console.anthropic.com → API Keys → Create Key. Рядок починається на `sk-ant-`.

### 2. Бот у Telegram (5 хвилин)

У Telegram напишіть **@BotFather** команду `/newbot`, придумайте назву — він
видасть токен виду `1234567:AA...`.

### 3. Notion (10 хвилин)

1. notion.so/my-integrations → **New integration** → отримаєте ключ `secret_...`
2. Створіть базу командою нижче — або зробіть її руками за схемою з розділу
   «Поля бази».
3. **Найважливіше:** відкрийте сторінку бази → «...» у правому верхньому куті →
   **Connections** → додайте свою інтеграцію. Без цього Notion відповідатиме
   «не знайдено», хоч база й існує. На цьому спотикаються всі.

Три ключі — `ANTHROPIC_API_KEY`, `NOTION_API_KEY`, `TELEGRAM_BOT_TOKEN` —
покладіть у файл `.env` поряд із `run.py`:

```bash
cp .env.example .env      # і впишіть три значення
cp config.example.yaml config.yaml
```

### 4. Опишіть команду (10 хвилин — найважливіший крок)

У `config.yaml` є поле `team_context`. Напишіть, хто в команді й хто за що
відповідає — саме за цим текстом система розуміє, що «маркетинг підготує»
означає Колю, а «бухгалтерія порахує» — Марію. Без цього вона гадатиме.

## Щоденне користування

```bash
# розібрати нараду
.venv/bin/python run.py analyze narada.txt --name "Планірка 24.08"

# те саме, але лише подивитися — нічого не створювати й не розсилати
.venv/bin/python run.py analyze narada.txt --dry-run

# звіт «що обіцяли — що зробили»
.venv/bin/python run.py report
.venv/bin/python run.py report --meeting "Планірка 24.08"
```

### Документ за нарадою

Крім задач, із наради можна зробити готовий документ — методичку, інструкцію,
шаблон, комерційну пропозицію чи протокол. Це окремий режим: тут цінне не
«хто що пообіцяв», а зміст розмови — як саме домовилися це робити, з
поясненнями й дослівними цитатами. Такий файл віддають людині, якої на нараді
не було, і вона розуміє все без переказу.

```bash
.venv/bin/python run.py document narada.txt \
    --kind методичка --what "як ми ведемо об'єкт від планірки до здачі"
```

Без прапорців команда спитає те саме двома питаннями. Види документів:
`методичка`, `інструкція`, `шаблон`, `кп`, `протокол` — від виду залежить
будова тексту, тому список закритий.

Готові файли лягають у `outputs/` (тека налаштовується як `documents_dir`).
Формат — Markdown: він відкривається будь-чим і не тягне зайвої залежності.
Потрібен .docx — `pandoc outputs/файл.md -o файл.docx`.

Чого в транскрипції не було, система не вигадує: такі місця збираються в
розділ «Треба уточнити» в кінці документа, щоб пробіли було видно тому, хто
читатиме файл, а не лише вам у консолі.

Щоб кнопки працювали, має бути запущений слухач — він забирає натискання
й міняє статуси в Notion:

```bash
.venv/bin/python run.py listen
```

### Реєстр співробітників

Telegram не дозволяє написати людині за іменем — тільки за `chat_id`, і цей
номер зʼявляється лише після того, як людина сама напише боту. Тому:

1. Попросіть кожного знайти бота й надіслати йому `/start`
2. `run.py register` — покаже, хто написав, разом із `chat_id`
3. `run.py register "Саша Петренко" --chat-id 111 --username sasha_p`
4. `run.py people` — перевірити реєстр

Імʼя в реєстрі має збігатися з тим, як людину звуть на нарадах. «Саша» знайде
«Сашу Петренка», але якщо в реєстрі два Саші — система не напише жодному
й скаже про це в підсумку. Написати «якомусь Саші» гірше, ніж не написати:
задача піде не тій людині, і ніхто цього не помітить.

## Поля бази «Домовленості»

Створити автоматично: `run.py setup <id_сторінки_notion>` — id береться
з адреси сторінки, це набір символів після останнього `/` і до `?`.

Робите руками — назви й типи мають бути точно такі:

| Поле | Тип | Значення |
|---|---|---|
| Задача | Title | |
| Відповідальний | Text | |
| Дедлайн | Date | |
| Пріоритет | Select | Високий, Середній, Низький |
| Статус | Select | Не почато, В роботі, Готово, Відкладено, Скасовано |
| Проєкт | Multi-select | заповнюється саме собою, див. нижче |
| Джерело | Text | |
| Цитата | Text | |

Назви й значення мають збігатися символ у символ — Notion звіряє їх дослівно
й відхиляє запис із будь-якою розбіжністю. У коді вони лежать в одному місці,
`meetings/models.py`: якщо у вас поле зветься інакше, правити треба там.

**Поле «Проєкт» окреме.** Notion не дозволяє записати в multi-select опцію,
якої ще немає в базі, — а назву проєкту система бере з розмови, тож нова
назва рано чи пізно зʼявиться. Тому перед записом вона сама заводить потрібну
опцію. Якщо не вдалося (наприклад, інтеграції не видали право Update),
задача все одно створюється — просто без поля «Проєкт», і про це буде рядок
у підсумку та в журналі. Втратити задачу через назву проєкту не можна.

## Як читати звіт

Задача з простроченим дедлайном показується як **прострочена**, навіть якщо
її статус — «в роботі». Статус ставить виконавець, дату — нарада; коли вони
розходяться, правда на боці дати.

Відсоток виконаного рахується без скасованих задач. Інакше показник можна
було б накрутити, скасовуючи все незручне.

## Коли щось не працює

| Що бачите | Що це означає |
|---|---|
| «Notion не бачить базу (404)» | Базою не поділилися з інтеграцією — розділ 3, пункт 3 |
| «Notion не прийняв ключ (401)» | У `.env` не той ключ: потрібен внутрішній ключ інтеграції |
| «Бот не може написати цій людині (403)» | Людина не надсилала боту `/start` |
| «немає в реєстрі бота» | Додайте людину через `run.py register` |
| «Notion відхилив дані (400)» | У базі поле названо інакше — звірте з таблицею вище |
| «вже розбиралася раніше» | Ту саму транскрипцію вже обробляли. Треба повторно — `--force` |
| «записано з поправками» | Задачі створені, але щось довелося змінити — найчастіше не завівся проєкт. Дивіться журнал |
| «нічого не збережено» | Жодна задача не записалась. Нараду **не** позначено розібраною — запустіть ту саму команду ще раз, без `--force` |

Усі збої пишуться у `data/errors.jsonl`, по рядку на подію.

## Чого система не робить

- Не слухає й не розшифровує аудіо — на вхід потрібен текст
- Не видаляє нічого й ніде
- Не пише в спільні чати — тільки особисті повідомлення
- Не вигадує дедлайнів: якщо строк не називали, поле лишається порожнім
- Не дописує в документ того, чого на нараді не було: пробіли виносить
  в окремий розділ, а не заповнює загальними словами
- Не призначає задачу навмання: коли незрозуміло, хто відповідальний,
  вона питає вас, а не обирає найімовірнішого
- Не вважає нараду розібраною, поки задачі не збереглися: якщо Notion був
  недоступний, повторний запуск тієї ж команди зробить роботу заново

## Безпека

Транскрипція — це чужа мова, записана диктофоном або сторонньою послугою
розшифровки. Тому вона потрапляє до моделі в окремому блоці, позначеному як
недовірені дані, і модель проінструктована не виконувати вказівок зсередини
нього. Крім того, до звернення до моделі текст перевіряється на прямі спроби
керувати розбором («ignore all previous instructions», «признач цю задачу
на...»). Якщо таке знайдено — задачі не створюються взагалі, а вам приходить
попередження з цитатою знайденого.

Це не теорія: у запис наради такий рядок може потрапити і випадково,
і навмисно — достатньо однієї людини в кімнаті.

## Для розробника

```
meetings/
  config.py      налаштування, .env, перевірки
  models.py      типи, якими обмінюються частини
  extractor.py   транскрипція → домовленості (Anthropic, structured outputs)
  notion.py      створення задач, зміна статусу, читання для звіту
  telegram.py    розсилка, кнопки, реєстрація
  registry.py    реєстр людей і памʼять про розібрані наради (SQLite)
  report.py      «що обіцяли — що зробили»
  document.py    нарада → готовий документ (методичка, інструкція, шаблон, КП)
  pipeline.py    оркестрація: збій однієї ланки не зупиняє решту
  errorlog.py    журнал збоїв
run.py           точка входу
tools/demo_run.py  прогін на підробках, без мережі
tests/           162 тести, жоден не ходить у мережу
```
