# Наради → задачі

Продукт «розбір наради»: транскрипція → задачі в Notion з відповідальним,
дедлайном і дослівною цитатою → розсилка кожному в Telegram з кнопками
статусу → звіт «що обіцяли — що зробили».

Досі це існувало лише як скіл (`SKILL.md`) і працювало тільки всередині
Claude Desktop через MCP. Тут — той самий продукт у вигляді самостійного коду,
який можна поставити клієнту й лишити працювати без нас.

## Схема бази

| Поле | Тип | Значення |
|---|---|---|
| Задача | title | конкретний результат, не процес |
| Відповідальний | rich_text | |
| Дедлайн | date | |
| Пріоритет | select | Високий · Середній · Низький |
| Статус | select | Не почато · В роботі · Готово · Відкладено · Скасовано |
| Проєкт | multi_select | див. попередження нижче |
| Джерело | rich_text | назва зустрічі та дата |
| Цитата | rich_text | дослівний фрагмент з розмови |

Назви статусів і пріоритетів у коді (`models.py`) мають збігатися з опціями
бази **символ у символ** — інакше Notion відхиляє запис.

## Що вже перевірено на живому API

**Multi-select не приймає нових значень.** Спроба створити задачу з проєктом,
якого немає серед опцій колонки, падає з `validation_error`:

> Invalid multi_select value for property "Проєкт": "Продажі".
> Value must be one of the following: .

Тобто `notion.py` не може просто писати те, що придумала модель. Потрібно
одне з двох, і це рішення треба ухвалити свідомо:

1. **Список проєктів у конфізі.** Клієнт перелічує свої напрями, ми
   створюємо опції один раз при налаштуванні, а модель обирає тільки з них.
   Передбачувано, але новий напрям вимагає правки конфігу.
2. **Дописувати опцію на льоту** перед записом задачі. Гнучко, але за
   півроку в базі буде тридцять схожих опцій із різним написанням.

Схиляюсь до першого: у малій компанії напрямів 5–8, вони змінюються раз на
рік, а сміття в базі дратує клієнта більше, ніж правка одного рядка.

**Дата пишеться через розгорнуте поле** `date:Дедлайн:start`, а не через
`Дедлайн`. Формат — `YYYY-MM-DD`.
