**Наслідок за ТЗ §48:** переходити до Sprint 1 не можна, доки Gate 0 не закритий.

## 0. Що змінилось відносно ранкової версії звіту

Ранкова версія цього документа стверджувала, що Gate 0 заблокований
**мережею**: усі хости провайдерів різались проксі `403` на етапі `CONNECT`.
Це було правдою для середовища, у якому писався PoC.

**Це вже не так.** Прогін з поточного середовища:

```
The Odds API v4                  api.the-odds-api.com        YES  TLS-з'єднання встановлено
API-Football (api-sports.io)     v3.football.api-sports.io   YES  TLS-з'єднання встановлено
SportMonks Football              api.sportmonks.com          YES  TLS-з'єднання встановлено
```

Мережа відкрита до всіх трьох. Залишився **рівно один блокер — API-ключі**.
Це важлива різниця: раніше про провайдерів не було відомо **нічого**, тепер
відомо, що вони досяжні, і не вистачає лише доступу.

Стара діагностика збережена нижче в розділі 6 — вона пояснює, чому PoC
працює на синтетичному датасеті.

## 1. Короткий висновок

Gate 0 вимагає перевірити 2–3 провайдери на 20–30 реальних матчах. Харнес
написаний, прогнаний і готовий; хости досяжні; ключів немає, тому жодного
реального матчу не опитано.

**Матчів перевірено: 0 з 25.** Таблиця покриття лишається порожньою, і це
свідома відмова її заповнювати: ТЗ §1 прямо забороняє вигадувати дані.
Desk-research з документації провайдерів наведений окремо в розділі 4 і
**результатом Gate 0 не є**.

## 2. Що вміє харнес

`gate0/validate_providers.py` виконує рівно те, що вимагає ТЗ §3: бере 20–30
матчів, опитує провайдерів, перевіряє наявність ринків і timestamps, друкує
таблицю у форматі §3 і повертає ненульовий exit code, якщо гейт не пройдений.

Після технічного аудиту 29.08.2026 харнес суттєво перероблений — сім
виправлень, кожне з яких раніше давало **неправильну відповідь**, а не просто
неповну:

| Було | Стало |
|---|---|
| Запит ішов з `markets=totals,spreads`, а перевірялись `team_totals` і `btts` — їх у відповіді не могло бути в принципі, тому обидва ринки **завжди** виходили `NO` | Додаткові ринки The Odds API v4 живуть на окремому per-event endpoint — запит іде туди |
| xG вважався підтвердженим, якщо `/fixtures/statistics` віддав непорожній масив | Шукається саме тип `expected_goals`, і перевірка йде на **зіграних** матчах — у майбутнього матчу статистики немає за визначенням |
| `Historical odds` для API-Football виставлявся `PARTIAL` константою в коді | Тільки живим запитом |
| SportMonks probe не існував (`probe=None`) | Реалізований; незнайома форма відповіді лишає `UNKNOWN`, а не здогадку |
| Покриття ринків перевірялось на **одному** fixture | Перевіряється на вибірці 20–30 матчів; статус ринку = частка матчів, де він знайшовся (`YES` від 80%) |
| Статистика (xG / склади / травми) не входила у формальний гейт | Входить. Гейт рахується **по стеку**: здатність закрита, якщо є хоч в одного провайдера |
| Скрипт падав на Windows без `PYTHONUTF8=1` | stdout переводиться в UTF-8 усередині скрипта |

Останній рядок таблиці — не косметика: гейт, який не запускається однією
командою з README, на практиці не запускають.

Клітинки, які не перевірені, позначені `UNKNOWN` / `NO_KEY` / `BLOCKED`, а не
`NO`. Це різні речі, і плутати їх у Gate 0 не можна.

Закривається однією командою, без дописування коду:

```bash
export THE_ODDS_API_KEY=...
export API_FOOTBALL_KEY=...
export SPORTMONKS_API_KEY=...
python gate0/validate_providers.py --matches 25 \
    --md-out gate0/GATE0_RESULT.md --json-out gate0/gate0_result.json
```

## 4. Desk research — ⚠️ НЕ ПЕРЕВІРЕНО ЖИВИМИ ЗАПИТАМИ

Нижче — очікування з документації провайдерів. Це орієнтир для вибору, кого
тестувати першим, **а не результат Gate 0**. Кожен рядок потребує підтвердження
харнесом, перш ніж на нього можна спиратися.

| Provider | Fixtures | Stake odds | Asian totals | Team totals | BTTS | Historical odds | xG | Lineups | Injuries | Price/limits |
|---|---|---|---|---|---|---|---|---|---|---|
| The Odds API v4 | очік. YES | ⚠️ під питанням | очік. PARTIAL | ⚠️ залежить від плану | ⚠️ | **очік. YES** (окремий endpoint) | NO | NO | NO | NO |
| API-Football | очік. YES | ⚠️ під питанням | ⚠️ | ⚠️ | очік. YES | ⚠️ без руху лінії | очік. YES | очік. YES | очік. YES | NO |
| SportMonks | очік. YES | ⚠️ | ⚠️ | ⚠️ | очік. YES | ⚠️ | очік. YES | очік. YES | очік. YES | NO |

Головне, що видно вже зараз: **жоден провайдер не закриває все сам**.
Найімовірніша робоча конфігурація — **два провайдери**: один odds-first
(historical odds + рух лінії), другий stats-first (xG, склади, травми). Саме тому
`OddsProvider` і `StatsProvider` у ТЗ §6 розділені — архітектура це вже враховує,
і PoC її дотримується. Харнес тепер рахує гейт так само — по стеку, а не по
кожному провайдеру окремо.

### Окремо про Stake (ТЗ §0, §33)

Stake як bookmaker у публічних агрегаторах зустрічається нестабільно. ТЗ §3 це
вже передбачає: *«Якщо Stake не доступний, система має зберігати preferred
bookmaker окремо і використовувати best available price»*. У PoC це закладено:
`bookmakers.is_preferred` і `bookmakers.is_sharp` — окремі поля, preferred
bookmaker не зашитий у логіку.

## 5. Що потрібно від замовника, щоб закрити Gate 0

1. **API-ключі — єдине, чого бракує.** Мінімум два: один odds-провайдер, один
   stats-провайдер. Достатньо trial/free tier: для Gate 0 потрібні 25 матчів,
   а не продакшн-обсяг. The Odds API має безкоштовний тариф на 500 запитів/міс.
2. **Підтвердження цільових ліг** — зараз у харнесі EPL / La Liga / Bundesliga.
3. **Окремо врахувати historical odds.** У The Odds API це платний тариф;
   якщо ключ буде без нього, харнес чесно поставить `NO`, і цей рядок гейта
   не закриється. Це варто перевірити ДО оплати основного плану.

Мережевий доступ більше в цьому списку не потрібен — він є.

Після отримання ключів Gate 0 закривається за ~15 хвилин однією командою.

## 6. Історична довідка: чому PoC працює на синтетичних даних

У середовищі, де писався PoC, усі хости провайдерів різались egress-політикою:
проксі відповідав `403` ще на етапі `CONNECT`, запит не доходив до провайдера.

```
[BLOCKED] The Odds API v4              api.the-odds-api.com       403 на CONNECT
[BLOCKED] API-Football (api-sports.io) v3.football.api-sports.io  403 на CONNECT
[BLOCKED] SportMonks Football          api.sportmonks.com         403 на CONNECT
```

Відмінність, яка тут була принциповою:

| Код | Що означає | Висновок для Gate 0 |
|---|---|---|
| `401 / 403` **від провайдера** | хост доступний, потрібен/невірний ключ | провайдер живий, треба ключ |
| `403` **на CONNECT від проксі** | запит не вийшов з мережі | про провайдера **не відомо нічого** |

Тоді був другий випадок. Через це в PoC немає реальних коефіцієнтів: увесь
ланцюг працює на синтетичному датасеті у форматі відповіді The Odds API v4,
через той самий парсер — підмінена лише мережа. Мітка `SYNTHETIC_REPLAY`
протягнута від файлу даних через БД до кожної відповіді API.

Перемикання на реальні дані — один рядок конфігу:

```bash
ODDS_PROVIDER=the_odds_api
ODDS_API_KEY=<ключ>
```

### Побічна знахідка від 29.08.2026

Data-guard, доданий за пунктом 3 аудиту, виявив дефект самого синтетичного
датасету: генератор рахував момент опитування як `kickoff - offset`, і при
`--days-ahead 3` навіть найраніший зріз опинявся **на добу в майбутньому**.
Жоден реальний провайдер не повертає `last_update` з майбутнього, тобто
датасет не міг би приїхати з живого API — а він заявлений як такий за формою.

Поки перевірки віку ціни не існувало, це нічим не проявлялось. Тепер
від'ємний вік коректно трактується як `PROVIDER_ERROR_FUTURE_TIMESTAMP`.
Генератор виправлений: зрізи відлічуються назад від моменту генерації, усі
в минулому і до kickoff.

## 7. Критерій приймання Gate 0 (з ТЗ §3)

> *Обраний provider повинен реально покривати ключові ринки.*

Харнес перевіряє це формально:

```python
GATE0_REQUIRED_ODDS  = [Fixtures, Asian totals, Team totals, BTTS, Historical odds]
GATE0_REQUIRED_STATS = [xG, Lineups, Injuries]
```

Якщо хоч одна здатність не закрита `YES` **жодним** провайдером стеку — exit
code 1 і «Gate 0 НЕ ПРОЙДЕНО». Додатково гейт валиться, якщо вибірка менша за
20 матчів: перевірка на трьох матчах не є перевіркою за §3. Пройти його
«на око» неможливо.
